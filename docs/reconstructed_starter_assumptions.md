# Reconstructed starter — assumptions register

**These files are reconstructions, not the organiser's files.** The official Problem 1
specification references `starter/schemas.py`, `starter/run_local_harness.py` and a
public question set, but none of them were available in this workspace. `starter/`
therefore contains the smallest compatibility layer that satisfies what the
specification *documents*; every file carries `RECONSTRUCTED_STARTER = True`.
Passing `starter/run_local_harness.py` is **not** a guarantee of passing the
organiser's harness. Only `stage1/atlas.py` imports `starter.schemas`, so replacing
the layer with the official one should require changes there alone
(`_from_official` / `_to_official`).

| # | Assumption | Evidence from the official specification | Why it was necessary | How to replace |
|---|---|---|---|---|
| 1 | `Question` has `question_id: str`, `text: str` and an optional `kind` hint | The spec shows `Atlas.answer(question: Question) -> Answer`, answers carry `question_id`, and it lists four question *kinds* (count/lookup/finding/trap); the question field names themselves are not shown | A typed input object is required to call `answer()`; the backend never relies on `kind` | Drop in the official `schemas.py`; adjust `_from_official()` in `stage1/atlas.py` if the field names differ |
| 2 | `Answer.answer` is `list[str] \| list[RecordRef] \| int \| str \| None` | Worked examples: finding → list of subject IDs, trap → `[]`, count → "the exact integer", lookup → "the exact list of record references" | Four answer shapes are documented; a union covers them without inventing extra fields | Narrow/widen the union in `schemas.py`; `_to_official()` already converts internal refs and ints |
| 3 | `RecordRef` = `domain` + (`usubjid`, `seq`) for data, or `domain="DOC"` + `document`, `section` | Spec shows `RecordRef(domain="LB", usubjid="042-S07-001", seq=31)` and `RecordRef(domain="DOC", document="lab-manual", section="units")` | Both shapes are shown verbatim; a validator enforces the shape-specific required fields | If the official model is stricter (e.g. no optional fields), map in `_ref_to_official()` |
| 4 | `steps_used` and `tokens_used` default to `0`; `confidence` is bounded to `[0, 1]` | Example answer JSON: `"confidence": 0.9, "steps_used": 6, "tokens_used": 0`; the trap example omits both counters | The example omits them once, so they cannot be strictly required | If they are required, they are always populated anyway |
| 5 | Pydantic v2 `BaseModel` | The spec's `Question`/`Answer` are typed objects with JSON examples; the framework is not stated | Validation + `model_dump()` give schema-valid JSON with no extra code | Backend does not use pydantic outside `stage1/atlas.py` and `starter/`; a dataclass starter would only change the conversion function |
| 6 | Harness evidence check = every cited `(domain, USUBJID, SEQ)` exists in the raw CSVs and every DOC document exists in `documents/` | Spec: "Every RecordRef … must exist in the study and actually support the claim" — evidence validity is scored | Existence can be checked mechanically and independently of the graph; "supports the claim" cannot be verified generically by a harness, so the backend's own validator (`backend/evidence/validator.py`) re-checks each claim before answering | The official harness may check differently; the internal validator does not depend on the harness |
| 7 | Output file names `stage1_public.json` and `graph_stats.json`, with `graph_stats.json` = the dict returned by `build()` plus provenance keys | Spec "What you submit": `graph_stats.json — nodes, edges, subjects covered, build time, the cut you built at`; `stage1_public.json — your own run against the ten public questions` | Names are given; internal structure is not | Both are produced by scripts (`scripts/*.py`) — regenerate against the official question file when available |
| 8 | Public question set = only the four example questions documented in the spec (`Q018`, `Q031`, the count and lookup examples) | The spec references "ten public questions" but lists only these four with text; two carry IDs | Inventing six more would be guessing hidden questions | Replace `starter/public_questions.json`; `scripts/run_public_questions.py` accepts any `{"questions": [...]}` file |
| 9 | `DD/MM/YYYY` is parsed day-first | Spec: "Dates. More than one format appears." The practice data shows ISO and `DD-MON-YYYY` only | Slash dates are not present in the practice data; a deterministic choice avoids silent ambiguity (documented in `backend/normalization/dates.py`) | Change the order in `parse_date()` |
| 10 | `build(cut=None)` = every record regardless of `cut_available`; the reported `cut` is the highest `cut_available` seen | README: "keep rows where `cut_available <= 3`" defines cut filtering; the meaning of no cut is not defined | The practice data contains `cut_available` values above the last row of `cuts.csv`, so "latest listed cut" would silently drop records | `backend/cuts/cut_manager.py::build_cut_view` |
| 11 | Protocol version for a cut beyond the last row of `cuts.csv` = the last listed version; below the first row = the first listed version | README: "`cuts.csv` — which protocol version is in force at each cut" | Records exist at cuts 13–15 while `cuts.csv` stops at 12 | `backend/cuts/version_manager.py::protocol_version_for_cut` |
| 12 | DM rows are cited with `seq=None` (DM has no `DMSEQ` column) | README: "`<DOMAIN>SEQ` numbers a subject's records … `(domain, USUBJID, seq)` identifies a record uniquely"; `DM.csv` has no sequence column | A DM row is still citable evidence (e.g. for duplicate subjects) | If the official schema requires an int, map DM to `seq=1` in `_ref_to_official()` |
